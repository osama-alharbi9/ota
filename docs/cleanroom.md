# Clean-room log

Every design decision in the Shorebird-independence work, with the public source or the original reasoning behind it. Newest entries go at the bottom of each section.

## Rules

- **Allowed sources.** Stock Dart SDK and Flutter engine source. Shorebird's public repos: CLI, updater, Flutter fork and its engine glue, ffi_test. Shorebird's public docs, issues and PR text.
- **Forbidden.** Decompiling, disassembling or inspecting Shorebird's closed binaries: aot-tools, prebuilt engines, Dart SDK artifacts. Reverse engineering the .vmcode format from real files.
- **Formats.** We design our own file formats. No compatibility with Shorebird's formats is needed.
- **Licenses.** Upstream license headers stay intact. New files are under our own license.

### What was deliberately not examined

These files exist on this Mac from earlier use of the stock CLI. They were not opened, dumped, disassembled or diffed. Only their names and sizes were listed.

- The aot-tools cache: `~/.shorebird/bin/cache/artifacts/aot-tools/*/aot-tools.dill`.
- The prebuilt patch tool: `~/.shorebird/bin/cache/artifacts/patch/patch`. We build our own from the public updater repo instead.
- The prebuilt engine artifacts and Dart SDK under `~/.shorebird/bin/cache/flutter/*/bin/cache/`.
- Every `.vmcode` file and every Shorebird-built `Flutter.framework`, `libflutter.so` and `App.framework`.

## Track 1: Android independence

### T1-01. How a patch is loaded on Android, from public glue

Sources are in the fork under `engine/src/flutter`. These files are Shorebird's; we keep their headers.

1. `shell/platform/android/flutter_main.cc` reads `shorebird.yaml`, the version name and the version code. It calls `ConfigureShorebird(...)` in `shell/common/shorebird/shorebird.cc`.
2. `ConfigureShorebird` builds an `AppConfig` with the release version, `original_libapp_paths`, and the storage and cache directories. It then calls the Rust updater through its C API in `updater/library/include/updater_engine.h`: `shorebird_init`, `shorebird_validate_next_boot_patch` and `shorebird_next_boot_patch_path`.
3. If a patch is active, Android **replaces** `settings.application_library_paths` with the patch path. iOS prepends it instead. That iOS branch sits under `SHOREBIRD_USE_INTERPRETER`, which `common/config.gni` defines only when `is_ios`.
4. `runtime/dart_snapshot.cc` calls `ReportLaunchStart()`. It then resolves the isolate snapshot through the stock `SearchMapping` path, which `dlopen`s the file. On Android the patch is therefore a complete `libapp.so`.
5. `shell/common/shell.cc` reports launch success or failure to the updater for rollback.
6. The updater downloads a compressed binary diff against the base `libapp.so`. It inflates the diff into a full file and checks the file's hash (`updater/library/src/updater.rs`, `updater/patch/README.md`).

**Conclusion.** The Android runtime path is stock Dart AOT loading plus public glue plus the public Rust updater. No private Dart VM behavior is involved.

### T1-02. Dart APIs the engine uses that stock Dart lacks

**Method.** We collected every `Dart_*` identifier in engine C, C++ and Objective-C++ sources outside `third_party` and `testing`. We compared that list with the symbols declared in stock `runtime/include/*.h` and `runtime/bin/elf_loader.h` at `c70f78e7`.

**Result.** Only two real API calls are missing: `Dart_SnapshotDataSize` and `Dart_SnapshotInstrSize`, both in `shell/common/shorebird/snapshots_data_handle.cc`. Three other names also failed to match, but none is a missing API. Two are comments in `runtime/dart_isolate.*` and `runtime/platform_isolate_manager_unittests.cc`. The third is Fuchsia-only and generated by the stock `_DL` macro.

**Decision.** The Flutter fork guards the two calls with `SHOREBIRD_USE_INTERPRETER`, the iOS-only define. `FileCallbacksImpl::Open` already returns `nullptr` off iOS, so this code never runs on Android.

### T1-03. Dart GN arguments the engine passes

**Method.** We listed the `gn_args['dart_*']` keys that `flutter/tools/gn` sets.

**Result.** Four keys do not appear in the stock `.gni` files we checked: `dart_include_wasm_opt`, `dart_platform_sdk`, `dart_use_mallinfo2` and `dart_version`. All four are also set by upstream Flutter. `gn gen` will confirm whether stock Dart declares them elsewhere.

**Other findings.**
- The fork passes `shorebird_runtime=true` only for iOS builds. No public `.gn` or `.gni` file declares it, so it must be declared in the private Dart fork. Android builds never pass it.
- Upstream Flutter's own `tools/gn` sets `dart_force_simulator = True` for iOS debug builds on arm64 devices. That line exists upstream, not only in the fork. It matters for Track 2.

### T1-06. Design choices for the self-built toolchain (original reasoning)

- **A separate CLI clone.** The CLI is a separate public clone at `~/engine-src/shorebird`, not a modified `~/.shorebird`. The working stock setup stays available for comparison, and nothing we do is overwritten by `shorebird upgrade`.
- **One monorepo clone.** A single clone at `~/engine-src/flutter` serves as both the Flutter framework used by the CLI and the engine source tree. That is how the monorepo is meant to be used. The CLI's `bin/cache/flutter/<rev>` is a symlink to it.
- **`engine.version` equals our HEAD, as an uncommitted edit.** `tools/gn` stamps `git rev-parse HEAD` into artifacts, for example the Maven POM version `1.0.0-<hash>`. flutter_tools reads the file instead, in `update_engine_version.sh`. A committed file cannot contain its own commit's hash. Keying on our own hash has a second benefit: any lookup that escapes to a third-party host asks for a hash nobody else has and fails loudly.
- **Our own artifact server, `engine/scripts/artifact_server.py`.** flutter_tools refreshes its cache by engine hash even in `--local-engine` mode (`flutter_command.dart` `verifyThenRunCommand`, with no local-engine exemption). So we serve our build outputs under the same paths upstream CI uploads to (`zip_archives/<p>` goes to `flutter_infra_release/flutter/<hash>/<p>`). Everything else gets a logged 404, so the log proves what was and was not ours. The only exceptions are two written allowlists: Google assets, and empty placeholders with a stated reason.
- **Native arm64 host tools.** We build with `host_cpu="arm64"`. Shorebird's CI forces `x64` for Intel Macs, which we do not need.
- **Scope of "binaries we built ourselves".** It covers the Flutter engine, the Dart SDK, the Rust updater and the patch tool. Third-party toolchains stay stock: Xcode and clang, the Android SDK and NDK, Gradle and Maven dependencies, and the depot_tools and CIPD build toolchain Google publishes. These are not Shorebird's, and the rules do not cover them.

### T1-07. The updater has no built-in default server

**Finding.** The first `libflutter.so` we built contained one Shorebird hostname, `https://api.shorebird.dev`. It is the updater's fallback when `shorebird.yaml` has no `base_url` (`updater/library/src/config.rs`, `DEFAULT_BASE_URL`). Our apps always set `base_url`, so it is never contacted. But a release that forgets the line would silently call a third-party host.

**Decision.** The updater fork removes the non-test default. If `base_url` is missing, `shorebird_init` fails and the app keeps running its bundled code. Test builds keep their mockito default.

**Verification.** `cargo test -p updater` passes all 220 tests on three consecutive runs. One earlier run had a single failure in `reports_patch_download_on_update` while the host build was loading the CPU. That test passes alone on both our code and upstream `185280e`, so we treat it as a timing flake.

**Application.** `gclient sync` checks `third_party/updater` out at the pinned `updater_rev`, so `sync.sh` re-applies the updater patch series every time.

### T1-08. Build observations

- **gn warnings.** `gn gen` reported no errors for Android or host. The only warning is `angle_build_all` having no effect, which upstream Flutter also sets.
- **`content_hash`.** Its value in `args.gn` is `e69de29b…`, the git hash of an empty blob. `bin/internal/content_aware_hash.sh` produces no input in a treeless fork clone. Nothing in the Android or host release path consumes it.
- **Full build.** The Android arm64 release build, 8181 ninja steps against stock Dart, finished with 0 failures on the first compile. The only fix needed first was the depot_tools ninja wrapper (see `env.sh`).

### T1-09. Where the forks live

Our changes live in two public forks, each a single commit on top of the pinned upstream revision:

- [`ota-flutter`](https://github.com/osama-alharbi9/ota-flutter), branch `ota/stable`, on the public fork pin `c2c56ab2`.
- [`ota-updater`](https://github.com/osama-alharbi9/ota-updater), branch `ota/stable`, on the public updater `185280e0`.

`DEPS` points `third_party/updater` at the updater fork and `third_party/dart` at stock Dart `c70f78e7`, so `gclient sync` needs no override and contacts no Shorebird host. To move them, change `.gclient` `url`, the base URL in `DEPS` and `cli/bin/internal/flutter_git_url`.

### T1-10. Names in the forks

Shorebird's additions carry the forks' own names in file contents and paths: engine glue, runtime, platform files, flutter_tools, the Gradle plugin, docs tools, and the updater's library and C API. Rules:

- **License and copyright lines are never changed.** Three lines keep "The Shorebird Authors" in the fork (`build_rust_updater.gni`, `build_rust_updater.py`, `list_rust_files.py`). MIT, Apache and BSD require them.
- Links to Shorebird's issue trackers became plain "upstream issue N". Links to its website or docs keep only their text. No URL, handle or hostname points at an address we don't own.
- Removed: Shorebird's CI, its test harness, and in the updater its CI and tooling config.
- In Flutter's own roadmap docs, the sentence recommending Shorebird as a partner was deleted, so Flutter's text is not falsified.

The names compiled into the published engine build are listed in `cli/packages/ota_cli/lib/src/toolchain_names.dart`. They can only change with a new engine build. `cargo test` on the updater: 221 passed.

### T1-11. Hosts Shorebird substituted, reverted to upstream Flutter's

Shorebird's fork replaced upstream Flutter's `https://storage.googleapis.com` with `https://download.shorebird.dev` (same path layout) as the default in: the Gradle plugin Maven host (`FlutterPluginConstants.kt DEFAULT_MAVEN_HOST`, `aar_init_script.gradle`), the flutter_tools artifact cache (`cache.dart`), the flutter doctor host check (`http_host_validator.dart`), the Dart SDK download (`bin/internal/update_dart_sdk.sh`, `.ps1`), the web artifacts step and docs tools. All are reverted to upstream Flutter's value. The ota CLI always sets `FLUTTER_STORAGE_BASE_URL` to OTA's artifact server, so these defaults matter only when the fork is used on its own.

### T1-12. Build-trace library vendored

flutter_tools had a git dependency on `github.com/shorebirdtech/shorebird` at `cff436f6` (`packages/shorebird_build_trace`), fetched by `pub get` on every fresh bootstrap. It is vendored into the fork as `packages/ota_build_trace` from that exact public revision, with its `LICENSE-MIT`, `LICENSE-APACHE` and `COPYRIGHT`, and referenced by path.

### T1-13. ota CLI on OTA's toolchain

- `bin/internal/flutter.version` = our fork commit; `bin/internal/flutter_git_url` = our git host; `bin/internal/artifacts_url` = OTA's artifact server. `OTA_FLUTTER_GIT_URL` and `OTA_ARTIFACTS_URL` override them. The bootstrap (`shared.sh`) and the Dart CLI read the same files.
- Every `flutter` subprocess gets `FLUTTER_STORAGE_BASE_URL` = the artifacts URL. The `patch` tool comes from `<artifacts>/ota/<engine>/patch-darwin-x64.zip`, built by `build_patch_tool.sh` from our updater branch.
- The project file `ota.yaml` is the bundled asset. No second config file is generated.
- Release, patch and preview accept Android (and AAR) only. iOS needs a patch interpreter OTA does not have; macOS, Windows and Linux need engines OTA does not build yet.

### T1-14. Three Android ABIs

arm64 (`out/android_release_arm64`), arm (`out/android_release`) and x86_64 (`out/android_release_x64`) are built with `build_android.sh <cpu>`, which fails if `strings` finds `shorebird` in the resulting `libflutter.so`. The Rust target `armv7-linux-androideabi` was added for arm. Only arm64 can be run here (the emulator on this Apple Silicon Mac); arm and x86_64 are checked by build ID inside the app bundle.

### T1-15. analyze_snapshot for 64-bit targets only; engine.version like upstream

**analyze_snapshot.** The first 32-bit arm build failed at `gn gen`: `//flutter/lib/snapshot:create_macos_analyze_snapshot_*_arm` needs `analyze_snapshot` for `dart_target_arch=arm`. Stock Dart defines it only for 64-bit AOT targets (`runtime/runtime_args.gni`: "The analyze_snapshot tool is only supported on 64 bit AOT builds"). The fork added Mac analyze_snapshot artifacts for every target CPU; that presumably relied on the private Dart SDK. Android never uses analyze_snapshot (it serves the iOS and macOS patch tooling), so the targets are now created for arm64 and x64 only. A comment in that block that read "Added by ota" after the rename now reads "Added in this fork (not in stock Flutter)": the code was written upstream, not by OTA.

**engine.version.** A fork clone must carry the right engine hash in `bin/internal/engine.version`, and a commit cannot contain its own hash. We follow upstream Flutter's engine roll: `ota/engine` is the engine source commit that gets built (artifacts and Maven POMs are keyed by its hash); `ota/stable` is `ota/engine` plus one commit writing that hash to `engine.version`. The ota CLI checks out `ota/stable`. `engine/scripts/publish_fork.sh` creates that commit and pushes both branches, `flutter_release/3.41.7` and the `3.41.7` tag to our git host.

### T1-17. What the artifact server serves, and why each deviation from upstream is safe

The request list comes from the server log of a fresh `ota --version` bootstrap and a trial `flutter build appbundle --release` for all three ABIs. Every rule was added only after its path showed up as a MISS.

**Served from our builds (SERVE).**
- `dart-sdk-darwin-arm64.zip`: our from-source Dart SDK (stock Dart `c70f78e7`). It is zipped in `make_mirror.sh` with upstream's `build/zip.py`. The GN target `flutter/build/archives:dart_sdk_archive` fails for a from-source SDK on macOS: it passes its entitlements file as an unrebased `//out/...` path. Upstream's Mac CI uses a prebuilt SDK and never takes that branch.
- `engine_stamp.json`: written by upstream's own generator (`et stamp`), run with our Dart SDK.
- `flutter_patched_sdk_product.zip`, `sky_engine.zip`, `flutter_gpu.zip`: upstream archive targets. The last two exist only in Android configs (upstream builds them in `android_debug`); we build them with arm64.
- `darwin-arm64/font-subset.zip`: `font-subset` and `const_finder.dart.snapshot`, a release build, as upstream.
- `darwin-arm64/artifacts.zip`: host tools that flutter_tools unpacks into `engine/darwin-x64`.
  - Upstream zips this only in a debug host build; its release variant holds just `gen_snapshot` and `analyze_snapshot`. We build release only, and a debug host engine would need more than 10 GB of disk we do not have.
  - `make_mirror.sh` therefore packs it with upstream's `zip.py` and upstream's file names, from the mode-independent tools of our release host build: `impellerc` and `shader_lib` (every Android release build compiles shaders with them), `libtessellator`, `libpath_ops`, `icudtl.dat`, `gen_snapshot` and `analyze_snapshot`.
  - `flutter_tester` and the JIT snapshots are left out: they exist only for debug and `flutter test`.
- `android-{arm,arm64,x64}-release/darwin-x64.zip` (gen_snapshot) and the Maven artifacts `io.flutter:{flutter_embedding_release,arm64_v8a_release,armeabi_v7a_release,x86_64_release}:1.0.0-<engine>`.
  - Every ABI config builds the embedding jar. The copies differ only by an empty `tmp_<random>/.empty` entry that the jar step leaks, so arm64's copy is served.
- `ota/<engine>/patch-darwin-x64.zip`: our `patch` tool.

**Placeholders.** A placeholder is a zip holding only `OTA_PLACEHOLDER.txt`. An empty zip fails, because flutter_tools' `unzip` exits non-zero on it.
- `flutter_patched_sdk.zip`: the non-product kernel platform, used by debug and profile builds and by `flutter test`.
- `android-{arm,arm64,x64}-profile/darwin-x64.zip`: profile-mode gen_snapshot. flutter_tools downloads the profile and release gen_snapshots for all ABIs whatever mode is built.

As a result, the OTA toolchain builds release only. Debug runs, profile builds and `flutter test` do not work with it. The ota CLI only builds releases and patches; developers keep stock Flutter for the rest.

**Proxied from Google (GOOGLE).** These are engine-independent files Google publishes for stock Flutter:
- Material fonts and the Gradle wrapper;
- the iOS USB tools (`libimobiledevice`, `libusbmuxd`, `libplist`, `openssl`, `libimobiledeviceglue`, `ios-deploy`). flutter_tools downloads them on every macOS host; Android builds do not use them.

**Result of the trial build.** The app bundle built with all artifacts from the server, with no MISS. `libflutter.so` in the bundle has our build ID for arm64, arm and x86_64, and none of them contains `shorebird`.

**Cosmetic.** `flutter --version` prints `Engine • hash e69de29bb2d1…`, the git hash of empty input: the content-aware engine hash comes out empty for this fork checkout. Every download is keyed by `engine.version` (`fcf8fdc84…`), so the line is informational only.

**publish_fork.sh.** The `engine.version` commit is now made with git plumbing (a temporary index and `commit-tree`). Publishing can therefore run while an engine build uses the working tree, and HEAD stays on `ota/engine`.

## Track 2: iOS mixed mode (public evidence collected so far)

- **H1, the interpreter is the Dart ARM64 simulator.** Stock `runtime/vm/simulator_arm64.cc` exists. `runtime/BUILD.gn` turns `dart_force_simulator` into `DART_INCLUDE_SIMULATOR`, plus `SIMULATOR_FFI` for arm64. Shorebird's archived public `ffi_test` README gives a recipe: a native arm64 `gen_snapshot` plus a `simarm64` `dart_precompiled_runtime_product` built with `dart_force_simulator=true`. Its `mixed_mode_results.txt` shows corelib tests passing. Its `failures.md` lists FFI callback failures and an R18 assertion.
- **H2, the base stays signed and the patch is data.** In the public glue, iOS keeps the base snapshot and prepends the patch, a `.vmcode` file loaded with stock `Dart_LoadELF`, to the library search paths. Only isolate data and instructions come from the patch (`runtime/shorebird/patch_cache.h`). Base snapshot pointers go to a private VM entry point, `Shorebird_SetBaseSnapshots(isolate_data, isolate_instr, vm_data, vm_instr)`, whose body is not public.
- **H3, a linker compares base and patch per function.** Shorebird's docs describe "a new 'linker' for Dart which is able to look at two separate Dart programs … at a per-function level", with link percentage typically 98 percent or more. The fork's public `shorebird/ci/internal/linux_build.sh` compiles `aot-tools.dill` from `pkg/aot_tools` in the private Dart fork.
- **H4, the compiler is changed to keep output similar.** The docs describe "Modifying the Dart compiler … take a second parameter 'previous compiled output' and make 'new compiled output' maximally similar". Public issue #1892 cites "Removing an ObjectPool constant drops linking from 99% to 75%". The performance docs name inlining and type flow analysis as sources of non-local change.
- **H5, dynamic modules as an alternative.** Stock has `runtime/vm/interpreter.cc`, `bytecode_reader.cc`, `pkg/dynamic_modules` and `pkg/dart2bytecode`, plus the GN argument `dart_dynamic_modules`, which defaults to false. The README calls it experimental and additive only: it "cannot replace an existing declaration". Upstream Flutter CI has `*_ddm.json` engine builders.
